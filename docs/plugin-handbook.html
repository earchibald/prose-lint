Prose Lint, as a plugin

Prose Lint marks the sentences in Claude's writing that sound like a machine wrote them. It used to be three hooks and a style file, added to a settings file by hand. It is now one Claude Code plugin. One command installs it. The key for the judge is in the system keychain. Claude can change the rules when you ask in plain words.

This page is about the plugin's design. The first handbook explains what the tool looks for and what we measured.

Five words used on this page

Plugin
A folder that Claude Code installs with one command. It can hold hooks, skills, a style file, and a server.
Hook
A small program that Claude Code runs by itself at a fixed moment, such as after Claude writes a file.
Skill
A page of instructions that Claude reads when a job calls for it. You can also start one yourself, for example /prose-lint:check.
Server
A small program that stays open during a session and gives Claude a few tools to call. Claude Code calls this kind of server an MCP server.
Judge
Jev, a small AI model from the company TypeSafe. It answers a yes or no question about one sentence with a number from 0 to 1.

Two corrections to the brief

Commands are not gone. They became skills.

The Claude Code documentation says that custom commands "have been merged into skills". A file in a commands/ folder still works, and the documentation calls that form "legacy". A skill does the same job, and it can have extra files and a list of the tools it may use. Claude can also start a skill by itself when a request fits its description. The plugin has five skills and no commands. Each skill is also a command that you can type, such as /prose-lint:rules.

The secret key reaches hooks and the server. It does not reach the shell.

You were right that a plugin can keep a secret. An option marked sensitive goes to the macOS Keychain, and it never appears in a settings file. But Claude Code hands that value to only two kinds of program: the plugin's hooks, and the plugin's server. A shell command that Claude runs gets nothing. We checked: inside a session, env | grep -c CLAUDE_PLUGIN printed 0.

So a skill that ran prose-lint report.md in the shell would have no key, and the judge would not run. This is the reason the plugin has a small server. A skill calls the server's lint tool, and the server has the key.

What I added beyond the brief

  • A tool that tests a rule before it is saved. You give it sentences that should match and sentences that should not. On its first live run it found a fault in our own matcher: a phrase that ends in a comma never matched.
  • A status tool. It reports whether a key is set and where it came from. It never shows the key.
  • Your rules are kept outside the plugin. An update replaces the plugin folder. Your own file is read on top of the plugin's rules, so an update cannot lose it.
  • Short messages that explain themselves. A helper agent does not get the style file, so it would not know the codes. Each message therefore explains the codes it used, and only those.
  • A report at the start of a session, built from the reply log.
  • A switch for every piece, as plugin options.

Install

The two commands, with the real output from this Mac 
$ claude plugin marketplace add ~/Workshop/001-prose-lint
✔ Successfully added marketplace: earchibald-tools (declared in user settings)

$ claude plugin install prose-lint@earchibald-tools --config api_key=YOUR_TYPESAFE_KEY
✔ Successfully installed plugin: prose-lint@earchibald-tools (scope: user)
5 userConfig options not yet set — run /plugin configure prose-lint@earchibald-tools
in Claude Code, or pass --config KEY=VALUE.

The five options that are "not yet set" all have a default, so nothing more is needed. Start a new session after the install. A session that is already open keeps its old hooks.

Do not paste the key into a chat with Claude. A chat is saved in a transcript. Use the install command above, or the configure screen below. Both send the key straight to the keychain.

The code is 570 lines of JavaScript with no outside packages, and the tests are 762 lines. The five skills, the rules reference, and the style file are about 4,300 words of instructions.

The parts and their connections

Skills and common jobs

You do not need to remember a skill's name. Say what you want, and Claude picks the skill from its description. Each skill is also a command.

Each message names the file once and explains only the codes it used. A helper agent does not get the style file, so a bare code would mean nothing to it.

Your own rules, and updates

Claude Code runs a copy of the plugin, and an update replaces that copy. So the plugin reads two rule files and joins them on every run.

FileWho changes itAn update
rules.json in the plugin folderWhoever maintains the pluginReplaces it
~/.claude/prose-lint/rules.local.jsonYou, or Claude through the rules skillLeaves it alone

In your file you can add a phrase or turn one off. You can add a question, or change one field of a question. You can also change a limit and add an ignored path. If your file has a mistake in it, the plugin uses its own rules alone, and status names the mistake.

To change the plugin itself

# 1. edit the code in ~/Workshop/001-prose-lint, and run the tests
npm test
# 2. raise "version" in .claude-plugin/plugin.json, and commit
# 3. tell Claude Code
claude plugin marketplace update earchibald-tools
claude plugin update prose-lint@earchibald-tools
✔ Plugin "prose-lint" updated from 0.2.0 to 0.2.1 for scope user. Restart to apply changes.

Without a new version number, Claude Code sees no change and keeps the old copy. To try a change with no install, run claude --plugin-dir ~/Workshop/001-prose-lint.

What I changed on this Mac

  • I installed the plugin for your user, with the key from the old key file. The key went to the keychain through the install command, and it was never printed.
  • I removed the three hand-made hook entries and the outputStyle line from ~/.claude/settings.json. Your other hooks are as they were. A dated copy of the file from before the change is beside it, named settings.json.bak-before-plugin-….
  • I moved the hand-installed style file to ~/.claude/prose-lint/plain-prose.md.hand-installed. The plugin brings its own.
  • I left the old key file, ~/.config/prose-lint/env, in place. It lets the shell command reach the judge. Delete it if you want the key in one place only.

Limits and open items

  • Open sessions need a restart. A session that was open during the move has neither the old hooks nor the new ones. That includes the session that built this plugin, so its last commits were not checked.
  • Two pieces have not been seen live under the plugin. The session-start report and the reply log are covered by tests. The short test sessions ended before the reply hook could write, because that hook runs in the background.
  • A small model could not call the server's tools. Haiku found the tools and then said it could not use them. Sonnet called all three with no trouble. The hooks do not depend on this.
  • The copy in the cache holds more than it needs. Claude Code copies the whole folder, with the tests and these handbooks. A later version can move the plugin into a subfolder of the repo.
  • The folder is still in Workshop. Your layout rules say to promote a project to ~/Code when it is real. After that move, remove the list with claude plugin marketplace remove earchibald-tools and add it again at its new path. You also have a list on GitHub, earchibald-plugins. The plugin can be added to that one, and then any of your machines can install it.
  • No pass mark is proven yet. This is the same limit as before. The report skill and the three logs are the data for setting the marks.
  • Every shell command still starts a small program. Claude Code can filter a hook by command, but our commits often start with cd folder &&, and the filter would miss them. The program leaves at once when it sees no git or gh.
  • The Hamlet test has its own copy of the phrase list. One of its tests compares the two lists, and that test looks for the tool in ~/Workshop or ~/Code. It does not look in the plugin cache.
