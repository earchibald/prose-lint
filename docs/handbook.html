Prose Lint

Prose Lint reads what Claude writes and marks the sentences that sound like a machine wrote them. It checks chat replies, documents, commit messages, and the text of the game Hamlet. It tells Claude what it found, so that Claude writes the sentence again in plain words.

Six words used on this page

Session
One conversation with Claude Code in a terminal.
Hook
A small program that Claude Code runs by itself at a fixed moment, such as after Claude writes a file.
Judge
Jev, a small AI model from the company TypeSafe. It answers a yes or no question about a sentence with a number from 0 to 1.
Finding
One marked sentence, with the name of the rule that marked it.
Hint
A shape that a program can see but cannot confirm. "Carries" is a hint, because a person can carry wood. Only the judge can turn a hint into a finding.
Style file
A page of writing rules that Claude Code adds to Claude's instructions at the start of every session.

The game is allowed to give a fire or a river an act. "The Night the Fire Ran" is approved text. That rule is for reports and chat, and the game's text has its own, smaller check.

How it works

The tool splits text into sentences and leaves out code, links, and tables. Then each sentence passes through three layers. Two layers are plain code and need no network. The third layer asks the judge.

Three details

  • A judge answer replaces a hint. The tool marks the word "carries" as a hint. If the judge scores the sentence under 0.70, the hint is dropped. "Esk carries the wood to the fire" scores 0.05.
  • A long sentence is judged in pieces. A pattern inside a long sentence gets a lower score. So the tool also sends each clause, and it keeps the best score.
  • All the rules are in one data file. The file is rules.json. It holds the phrases, the questions, and each pass mark. To ban a new pattern, add a row. No code changes.

Where it runs

One tool does the reading. Five pieces call it, each at a different moment.

The commit hook stops a message only once. If Claude sends the same text again, the hook lets it through and writes "kept" in the log. A commit message sometimes must quote a faulty sentence, and this rule allows that.

Install

Everything is on Eugene's Mac already. These steps are for a second machine, or for a repair.

  1. Get the folder. The tool needs Node 22 or newer and nothing else.

    git clone <the repo> ~/Workshop/001-prose-lint
cd ~/Workshop/001-prose-lint && npm test      # 69 tests, under one second

  2. Store the key for the judge. Keep it out of every settings file and out of every repo.

    mkdir -p ~/.config/prose-lint && chmod 700 ~/.config/prose-lint
echo 'TYPESAFE_API_KEY=...' > ~/.config/prose-lint/env
chmod 600 ~/.config/prose-lint/env

    Without a key the first two layers still run, and the last line of output says that the judge did not.

  3. Add the style file. Copy plain-prose.md to ~/.claude/output-styles/. Then set one line in ~/.claude/settings.json.

    "outputStyle": "Plain prose"

  4. Add the three hooks to the hooks part of the same settings file. Keep any hook that is already there.

    "Stop":        [{ "hooks": [{ "type": "command", "async": true, "timeout": 60,
                 "command": "node ~/Workshop/001-prose-lint/hooks/stop-log.js" }] }],
"PostToolUse": [{ "matcher": "Write|Edit|MultiEdit",
                 "hooks": [{ "type": "command", "timeout": 45,
                 "command": "node ~/Workshop/001-prose-lint/hooks/write-feedback.js" }] }],
"PreToolUse":  [{ "matcher": "Bash",
                 "hooks": [{ "type": "command", "timeout": 45,
                 "command": "node ~/Workshop/001-prose-lint/hooks/commit-check.js" }] }]

  5. Check it. Start a new session and ask Claude to write a Markdown file that holds the sentence "This check is load-bearing." Claude should get a finding at once.

The settings file names the folder by its full path. If the folder moves, change the three paths. A hook that cannot start fails without any message.

Use

From the command line

prose-lint report.md notes.md      # all three layers
prose-lint --no-jev report.md      # no network: phrases, counted rules, hints
git diff | prose-lint --json       # text in, JSON out
prose-lint-log --since 2026-09-20  # what the reply log has recorded

The exit code is 0 for clean text, 1 for findings, and 2 when the tool cannot run.

What we measured

Each number below has its conditions beside it. All of it was measured on 20 and 21 September 2026 with the judge model Jev 1.13.

Can the judge tell a faulty sentence from a plain one?

We wrote one faulty sentence for each pattern, and several plain ones. A score near 1 means "yes, this is the pattern".

"Here is my honest summary"
0.99 "Let me break down…"
0.97 "The catch: nobody ran it"
0.97 "A guard that cannot fail…"
0.93 "A number travels with…"
0.89 "A sweep … is a sweep that…"
0.84 Plain: "The soak has six seeds"
0.16 Plain: "Esk carries the wood"
0.05 Plain: "The wolf hides in the pines"
0.02

Two patterns did poorly. "Not X, it is Y" scored 0.68 on its planted sentence. A list of three for rhythm scored 0.36, so plain code looks for that one and reports it only as a hint.

Does the judge agree with human reviewers?

Three reviewers had already judged 39 lines of game text. They named 9 pairs of lines as repeats of each other. We gave the judge all 283 possible pairs. It ranked all 9 named pairs in its top 35. "The dry room" scored 0.88 for a modern word, and the next line scored 0.52.

The code

The tool is about 430 lines of JavaScript with no outside packages. Its tests are 525 lines: 69 tests that run in under one second and never touch the network. Each test was written first and seen to fail. The rule file is 259 lines.

Faults that the work found in itself

  • The first text finder for Hamlet missed 69 strings. Two were real em dashes in a menu. A reviewer found this with a second, independent finder.
  • The commit hook stopped a good message for "a sentence of 46 words". It was two sentences. The splitter did not know that a sentence can start with a lowercase file name.
  • The tool cut its own output at 65,536 bytes when another program read it.
  • The tool skipped "Good." and "Great question!" because both are under three words. Those are the compliments it must catch.

Limits

  • No pass mark is proven. Each min value is a first guess. Scores between 0.70 and 0.79 for "a thing written as a person" are often wrong. "Five suites landed on dev" scored 0.77.
  • The reply log cannot stop a reply. The reply is on screen before the hook runs. The style file does the real work for chat.
  • The style file does not reach helper agents. A helper agent has its own instructions. The write hook and the commit hook do reach it, and we tested that.
  • Text written by a shell command is not seen. If Claude writes a file with cat or sed, the write hook does not run.
  • Claude can learn to dodge the questions. A new habit that no question names will pass. The human review panel stays the final judge, and the rule file grows when someone sees a new habit.
  • Every shell command now starts a small program. The commit hook costs about 40 milliseconds on each one.

Appendix: a slimmer design

The system works, and it is heavier than it needs to be. It has four entries in a settings file, three long message formats, and full paths that break when a folder moves. This appendix proposes a lighter form. Nothing here is built yet.

What is heavy today

WeightMeasured
Each message repeats its instructions and the file pathA message for 3 findings is 911 characters. The path, written 4 times, is 328. The standing instructions are 323. The findings are the rest.
Each message lands in Claude's working memory and stays thereTwenty file writes with findings add about 4,500 tokens. Most of that is the same instructions and paths, repeated.
Installation is five manual stepsSee the install section above.
The commit hook runs on every shell commandAbout 40 ms each

Idea 1: teach the code once, then send only the code

The style file already reaches Claude at the start of every session. Put a short legend there: a two-letter code for each pattern, and what to do about it. Then a hook message needs only the line, the code, and a few words of the sentence.

Today: 911 characters 
prose-lint read the text you just wrote to
/Users/…/reports/2026-09-21-example.md and
found 3 banned patterns.
Rewrite each sentence as a plain fact about a
named thing, then continue. Leave a sentence as
it is only when it is a quotation or text the
user approved word for word.

/Users/…/example.md:5  phrase  (use: essential…)
    This check is load-bearing now.
/Users/…/example.md:5  aphorism 0.93  (replace…)
    A guard that cannot fail protects nothing.
/Users/…/example.md:5  thing_acts 0.70  (say…)
    This check is load-bearing now.
Proposed: 149 characters 
prose-lint example.md:
L5 PH "load-bearing"
L5 SA "A guard that cannot fail…"
L5 TP "This check is…"

Legend, taught once in the style file:
PH  banned phrase: use the plain word
SA  saying: state the fact in this case
TP  thing as person: say what it is or has
DF  saying as definition   HO  claim of honesty
AN  announcement           RV  staged reveal
CO  compliment             LS  long sentence
ED  em dash

The proposed message is one sixth of the size. The risk is that a bare code is easier to ignore than a full sentence. We can test that: send codes in half of the sessions for a week, and compare how often the next edit fixes the sentence. The write log already records each later edit.

Idea 2: a short report at the start of each session

The reply hook records every chat reply, and today nobody reads the record. A small hook at the start of a session could read the log and give Claude four lines about its own recent writing.

prose-lint, your last 40 replies in this project:
  TP 28  LS 59  ED 30  RV 16   (per 100 sentences: 5, 10, 5, 3)
  worst: "That check line carries the session name."
  down from last week: AN 12 → 3

The box above is a mock-up, and its last line uses example numbers. The report costs about 60 tokens once for each session. It uses Claude's own sentences as the examples. We expect Claude to learn more from a sentence it wrote yesterday than from a stock example. The report also puts the reply log to use.

Idea 3: package it as a Claude Code plugin

A plugin is a folder that Claude Code installs with one command. It can hold hooks, a style file, and commands. A hook inside a plugin names its own folder with ${CLAUDE_PLUGIN_ROOT}, so a moved folder breaks nothing.

The plugin folder, proposed 
prose-lint/
  .claude-plugin/plugin.json   name, version
  hooks/hooks.json             the hook entries
  hooks/dispatch.js            one program for all events
  output-styles/plain-prose.md the rules and the legend
  commands/check.md            /prose-lint:check <file>
  commands/report.md           /prose-lint:report
  lib/  rules.json  tests/
Install and remove, proposed 
/plugin install prose-lint@earchibald
# hooks, style file, and commands arrive together

/plugin disable prose-lint
# everything is off in one step

A plugin can mark its style file force-for-plugin. Then the style is active whenever the plugin is on, and nobody needs to edit a settings file.

Idea 4: fewer hooks

Claude Code lets a hook name the commands it cares about, with an if rule such as Bash(git commit *). Our commits often start with cd folder &&, and that rule would miss them. So the plugin should test the command text itself and leave at once when it sees no git or gh. It does this today.

An idea we measured and do not propose

We tried to send the judge only the sentences that plain code finds suspicious. A suspicious sentence has a listed verb, a colon, or fewer than seven words. Over 1,204 sentences this cut the requests by half. It also lost 64 of 176 findings, and 50 of those were things written as a person. The verb list is too short to find them. The hooks spent 8 cents in their first evening, across six sessions. So this saving is not worth the loss.

Other options, in brief

OptionGainCost or risk
An editor helper that Claude calls before it ships a long document. The helper lints, rewrites, and returns only the clean text.No findings enter the main session's memory.A rewrite by a helper can change a fact. The review panel found this once already.

A proposed order

  1. Build the plugin around the code we have. One dispatch program, the style file, and two commands. This removes the manual install and the full paths. It changes no behaviour.

  2. Add the legend and the short codes, with a setting that keeps the long form. Run both for a week and compare the fix rate from the write log.

  3. Add the session-start report. It needs only the log that exists.

  4. Set the pass marks from panel verdicts when enough of them exist.

The style file stays the most important piece in every version. It is the only piece that acts before Claude writes. Every hook acts after.
